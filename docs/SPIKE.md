# 第 0 周 Spike：事件溯源引擎原型

> 状态：✅ 引擎原型完成，22 个单元测试通过（`python -m pytest`）
> 范围：纯后端逻辑，无前端、无数据库、无外部依赖（仅标准库 + pytest）

## 一、目标

在写任何正式业务代码前，用最小成本验证项目生死攸关的两个假设：

1. **事件溯源模型**能否干净地支撑"提议 → 审核 → 合并 → 回滚"的协作闭环；
2. 冲突判定、回滚、临时备选三个最难的设计点在事件溯源语义下是否自洽。

本原型只回答第 1 点（技术可行性）；第 2 点（用户接受度）由交互原型 + UX 测试完成。

## 二、核心不变量（设计决策）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 事件流 **append-only**，绝不改写/删除历史事件 | 全程可追溯的前提；回滚不破坏历史 |
| 2 | 定稿状态 = 事件流**全量回放**结果 | 事件溯源的标准语义；任意版本可重放 |
| 3 | 提议未采纳前的事件**只存在于提议**，不进入定稿 | 个人修改不污染主行程 |
| 4 | **冲突检测发生在采纳动作执行时**，基于当前已回放定稿，而非提交时快照 | 采纳时刻定稿才是"合并目标"，提交时判定会漏掉中间变更 |
| 5 | 回滚 = **追加补偿事件**（逆操作），而非删除/重写事件 | 保持 append-only；回滚后可继续正常采纳新提议 |
| 6 | 临时备选 = **提交即采纳的紧急提议**（emergency），不是游离在审核外的第二套状态机 | 事件溯源保持单一真相；可回滚、可事后正式化 |
| 7 | AI/爬虫/OTA 与核心引擎完全解耦 | 核心协作不依赖任何第三方接口（架构原则） |

## 三、数据模型摘要

```
TripEngine (一个旅行项目)
├── stream: list[StreamEvent]      # 定稿事件流（append-only）
│     StreamEvent{seq, kind(created/updated/deleted), item_id, payload,
│                 proposal_id, adopted_at, meta{emergency|rollback}}
├── proposals: dict[id, Proposal]  # 提议（draft/pending/adopted/rejected/revoked）
│     Proposal{events: list[ChangeEvent], emergency, adopted_version, last_report}
├── snapshots: dict[version, TripState]  # 每次状态变更后的不可变副本
├── notifications: list[Notification]    # 应用内通知记录（原型仅记录）
└── _state: TripState                    # 实时定稿（回放结果）
      TripState{items: dict[id, Item]}
      Item{id, day, position, title, refs[], amount?, note}
```

- 版本号 = 事件流长度；`state_at(v)` 返回第 v 个事件后的定稿快照。
- `refs` 是**显式依赖建模**（如 D2 酒店 `refs=[d1_train]`），是"隐性依赖冲突"可自动检测的前提。

## 四、冲突规则（采纳时刻）

| 类型 | 定义 | 处理 |
|---|---|---|
| **硬冲突** | ① 多个待审核提议同时修改同一条目；② updated/deleted 的目标条目在当前定稿中已不存在；③ created 的条目已存在 | 禁止自动合并，抛 `HardConflictError`；`force=True + resolution_note` 模拟管理员人工判定放行并留痕 |
| **软冲突/依赖告警** | 被修改条目被其它条目显式引用（`refs`）；或单提议含多条变更需人工复核 | 抛 `ConfirmationRequiredError`，`confirmed=True` 后自动合并，告警记录在提议上 |
| **紧急场景** | emergency 提议 | 绕过硬冲突/复核拦截，**但冲突告警完整记录并通知**（现场应急不能被流程卡死） |

## 五、回滚语义

- `rollback_to(version)`：diff 当前状态与目标快照 → 生成补偿事件（还原字段/删除新增/重建已删）→ 追加进事件流 → 状态恢复。
- 目标版本之后**已采纳的提议保留在历史中**，其提交人收到 `rollback_affected` 通知。
- 快照为不可变副本，后续采纳不会污染历史版本。
- 已知限制：补偿事件基于"当前 vs 目标"的字段级 diff，若回滚目标之后有交叉修改，采用"以快照为准"的覆盖语义，交叉项由人工确认（与产品层"人工兜底"一致）。

## 六、临时备选（emergency）语义

- `submit_emergency()` = 提交即采纳，事件带 `meta.emergency`，全员立即可见。
- `formalize()` = 转为普通已采纳提议（移除紧急标记，之后不可撤销）。
- `revoke()` = 追加逆操作事件恢复采纳前状态，提议标记 `revoked`，历史保留。
- 覆盖场景：景区临时闭园、游玩超时、临时换路线。

## 七、测试覆盖（22 个）

| 文件 | 覆盖点 |
|---|---|
| `test_lifecycle.py` | 草稿不污染定稿、提交/拒绝留痕、单条干净采纳免确认、多条合并需确认、非法状态操作、空提议校验 |
| `test_conflicts.py` | 并发硬冲突、强制人工判定留痕、**采纳时刻判定**（提交时无冲突/采纳时冲突）、依赖告警需确认 |
| `test_rollback.py` | 补偿事件恢复状态、append-only 校验、受影响提议通知、回滚后继续采纳、快照不可变、未知版本/同版本边界 |
| `test_emergency.py` | 提交即采纳+事件标记、硬冲突下仍采纳但告警记录、正式化后不可撤销、撤销恢复状态/原字段值 |

## 八、已知限制与下一步

- 原型无持久化（内存态）、无用户/权限层、无通知推送——MVP 阶段再接。
- 快照全量存储（每事件一份深拷贝）仅适合原型；正式实现用"周期快照 + 增量重放"。
- 冲突中的并发提议判定目前只看"待审核"状态；草稿/已拒绝不参与。
- **下一步（UX 验证）**：用本引擎行为做 mock，制作简易交互原型，招募 3~5 名真实即将出行群体测试"提议-采纳-回滚"与旅途应急场景。
